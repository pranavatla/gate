The one-minute version

What problem this solves

Companies that put an LLM behind a product face three problems at once: who is allowed to call it and how much can they spend, which prompt is live and what happens when someone edits it, and how do you know the answers did not quietly get worse.

01 · CONTROL

One front door

Tenant keys, rate limits, monthly budgets with automatic model downgrade, PII redaction, failover across four providers, and an audit trail for every call.

02 · CHANGE

Safe prompt changes

Prompts are immutable versions. A new version can go to a small, sticky share of traffic first, be promoted, or be rolled back in one command, with every step audited.

03 · QUALITY

Proof, not hope

A nightly eval asks a fixed set of questions, grades the answers, compares them with a baseline, and raises an alert when quality drops or the check itself breaks.

Engineer's view: the pieces and why
  • Single arm64 EC2, Docker Compose: five services (gateway, Postgres with pgvector, Redis, Grafana, Caddy). One box keeps cost and operations small; the deploy path is the same one a larger fleet would use.
  • Caddy terminates HTTPS and only routes gate.atla.in to the gateway. Grafana is bound to localhost and reached through an SSM tunnel, never exposed publicly.
  • Database migrations are plain SQL files applied by hand and recorded in git. I know this lacks a migration runner; it is listed under limitations.
  • Grafana's database user is read-only and can only read views built for dashboards, so a mistake in a panel cannot change data.
Phase A

Prompts as versioned, rollback-able releases

Before this, a prompt was a text file inside someone's code. Changing it meant redeploying, with no record of what changed and no quick way back. Now a prompt is a released artifact. Pick a release and press Ship it, or click any step to see what it does.

doneneeds a lookstoppednot needed
Press “Ship it” to follow one prompt release.
IMMUTABLE

v3 is always exactly v3

A saved version can never be edited, only replaced by a newer one. Any answer can be traced to the precise text that produced it.

STICKY

A visitor never flips

The share of traffic is decided by a hash of the visitor, so the same person always gets the same version and a conversation never changes behaviour halfway.

FLAGS

Switches with a safety net

Flags can be set for one tenant or everyone. If the lookup ever fails, the gateway falls back to the safe default instead of failing the request.

Engineer's view: rollout mechanics
  • Per tenant and prompt name, the registry holds a stable version and an optional candidate with a percentage.
  • The bucket is a SHA-256 hash of the visitor identity, so assignment is sticky and needs no extra storage.
  • Commands: publish, rollout, promote, rollback, show; flags: set, clear, show. Every one writes to the audit log.
  • Version 1 of a prompt goes live immediately; later versions are “not live yet” until rolled out.
  • Example flag: the evals tenant has cache_bypass on, so eval questions never read or fill the cache and every run measures the model, not a remembered answer.
Phase B

An eval pipeline that runs while I sleep

Every night the same questions are asked, the answers are graded, and the score is compared with how it normally does. It only speaks up when something truly changed, or when the check itself breaks. Pick a night and press Run the night, or click any step to see what it does.

What the verdict means

Healthy · no alert
OKexit 0

Score is inside the normal range.

IMPROVEDexit 0

Score is better than normal.

BUILDING_BASELINEexit 0

Fewer than three clean runs exist yet, so there is nothing to compare with.

Needs attention · alert fires
REGRESSIONexit 3

Quality fell by more than the allowed tolerance.

NOISY_BASELINEexit 4

History is too jumpy to judge fairly.

UNRELIABLEexit 5

The run did not finish properly, so its score cannot be trusted.

Person decides · manual
ACCEPTEDcommand

“This lower score is the new normal.” Resets what future runs are compared with.

EXCLUDEDcommand

“Throw this run out.” Used for experiments so they never pollute the baseline.

GRADING

Two layers of checks

Hard rules first (must contain, must not contain, word limit). Then a judge model scores meaning, and it sees only the reference answer, never the prompt, so it cannot be talked into agreeing.

FAIRNESS

Tolerance that adapts

The allowed drop is the larger of 0.10 or twice the history's spread, so a naturally noisy test does not cry wolf and a stable one is held tight.

SCHEDULE

Nightly, with a dead-man's switch

A timer runs both sets at 22:00 UTC. A separate alert fires if no run has happened in 36 hours, so silence itself is caught.

Engineer's view: data model and baseline rules
  • Tables: eval_sets, eval_cases (immutable), eval_runs, eval_results. Each result keeps the answer, score, judge reason, latency, cost and the request id that links back to the audit log.
  • Baseline: last five done runs of the same set and route, ignoring excluded or regressed runs, starting from the latest accepted run, minimum three needed.
  • Baseline is by set and route, not prompt version. That is deliberate: a new prompt must beat the normal, but experiments must be explicitly excluded so they do not poison it.
  • Exit codes let the nightly script and systemd report failure as a failed unit, which feeds the alert.
  • Secrets: the eval key lives in a secrets store and is fetched at run time; it never touches a shell history or a file.
Case study

The bug the evals helped me find

The chatbot on atla.in sometimes told visitors that I used OpenAI, Anthropic, Gemini and Bedrock at Accenture. That is false: those providers belong to my own projects. A wrong claim about my experience, in front of recruiters, is exactly the kind of defect that nobody notices until it hurts.

Found

A guard test asked "did Pranav use an LLM at Accenture?" and the chatbot said yes in roughly one run in six.

Corrected my own claim

After four clean runs I thought the old prompt was immune. A later run failed. Four runs were not proof, so I fixed a rule before testing further.

Candidate v5

Added one explicit fact to the chatbot's knowledge. Passed the Accenture test in 3 of 3 runs.

But it failed a second test, 3 of 3

The greeting. The model replied as if the visitor were me:

"Hello Pranav! What would you like to know about me?"
Read the actual answers, not the scores

The rule said "ask what they want to know about Pranav", but nothing said who the assistant is. The model had a name and no role.

v6 and ship

One added rule: you are an assistant that tells visitors about Pranav. 3 of 3 clean runs, then deployed. Checked live on atla.in.

"Hello! I can tell you about Pranav and his work. What would you like to know about him?"
Decided before looking at results: ship only if the Accenture test passes in all three runs and no other case fails in two or more. Keep the old prompt if the Accenture test fails even once. Writing the rule first stopped me from rationalising a weaker result.

Learnings

What this build taught me

Practices I would keep

  • Write the pass rule before the test. It removes the temptation to move the goalposts.
  • Read the raw answer. Scores locate a problem; the stored text explains it.
  • Make the checker fail loudly. A half-finished run once passed silently, so it now exits non-zero and raises an alert.
  • Keep experiments out of the baseline. One banana-test prompt would have wrecked a week of history.
  • Ship the smallest change that fixes the cause. One rule fixed the greeting; no rewrite.
  • Keep unfinished work out of a release. I found an unrelated, half-built change sitting in the same folder and set it aside before deploying.

Honest limits

  • Small eval sets. 40 cases across 3 sets catch known failures, not unknown ones.
  • The judge is a model. It can wobble on thin references; rule checks back it up.
  • No automated unit tests yet. Quality is gated by evals and a health check, not by a test suite.
  • Single server. Right for this scale; a larger fleet would need more than one box.
  • Migrations are applied by hand. A tracked migration runner is the next improvement.
  • The eval tests prompt and model, not retrieval, so the Gita app needs its own set.
